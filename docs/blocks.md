# The blocks

Every block, what it does, and the Python it writes.

Every snippet below was generated by the real generator, not typed by hand.
If you change a block, regenerate this page's examples rather than editing
them — `editor/test/generator.test.js` is what keeps them honest.

---

## What a program looks like

Blocks become ordinary SPIKE Python. It runs unchanged on a real hub, and a
teacher can paste it into LEGO's own app. Three blocks — set speed, drive
25cm, turn right 90° — produce this whole file:

```python
import runloop
import motor_pair
import math
from hub import port

WHEEL_DIAMETER_MM = 56
AXLE_TRACK_MM = 160
MOTOR_SPEED_PERCENT = 50

movement_speed = 50

motor_pair.pair(motor_pair.PAIR_1, port.A, port.B)

def degrees_for_distance(millimetres):
    """How far the motors must turn to cover a distance on the floor."""
    return int(millimetres * 360 / (math.pi * WHEEL_DIAMETER_MM))

def velocity_from_percent(percent):
    """Turn a speed percentage into degrees per second.

    A SPIKE motor runs at roughly 1050 degrees per second at full power.
    """
    return int(max(0, min(100, percent)) * 10.5)

def degrees_for_turn(turn_degrees):
    """How far the motors must turn to spin the robot on the spot."""
    return int(turn_degrees * AXLE_TRACK_MM / WHEEL_DIAMETER_MM)


async def main():
    global movement_speed
    movement_speed = 40
    await motor_pair.move_for_degrees(
        motor_pair.PAIR_1, degrees_for_distance(250), 0,
        velocity=velocity_from_percent(movement_speed))
    await motor_pair.move_for_degrees(
        motor_pair.PAIR_1, degrees_for_turn(90), 100,
        velocity=velocity_from_percent(movement_speed))


runloop.run(main())
```

Things worth noticing, because they are deliberate:

- **Named constants, not magic numbers.** A student can see where 250mm came
  from and change the wheel size.
- **Helper functions with docstrings.** `degrees_for_distance` is the arithmetic
  a robotics lesson teaches anyway; here it is, written out.
- **Constant arithmetic is folded.** 25 centimetres reads as
  `degrees_for_distance(250)`, not `degrees_for_distance((25) * 10)`.
- **Helpers appear only when used**, and only once however many blocks need
  them.
- **`global` appears only if a block actually changes the speed.**

The generated source is always visible in the editor's **Python** tab, in a
read-only text box rather than behind a dialog, so it can be read with a
screen reader without leaving the page.

## Start

Every program needs one of these. Blocks that are not joined to it are left
out, and the editor says so rather than silently dropping them.

| Block | Generates |
| --- | --- |
| **when the program starts** | `async def main():` … `runloop.run(main())` |

Everything inside becomes the body of `main()`. That is why the movement and
wait blocks can `await`: they are only legal inside an async function.

## Movement

These drive the robot as a whole, using both drive motors together. They
assume motors on ports **A** (left) and **B** (right).

| Block | Generates |
| --- | --- |
| **drive (forward/backward) for ( ) (centimetres/rotations/seconds)** | `await motor_pair.move_for_degrees(motor_pair.PAIR_1, degrees_for_distance(250), 0, velocity=velocity_from_percent(movement_speed))` |
| **turn (left/right) for ( ) degrees** | `await motor_pair.move_for_degrees(motor_pair.PAIR_1, degrees_for_turn(90), 100, velocity=velocity_from_percent(movement_speed))` |
| **start driving (forward/backward)** | `motor_pair.move(motor_pair.PAIR_1, 0, velocity=velocity_from_percent(movement_speed))` |
| **start driving with steering ( )** | `motor_pair.move(motor_pair.PAIR_1, int(steering), velocity=velocity_from_percent(movement_speed))` |
| **stop driving** | `motor_pair.stop(motor_pair.PAIR_1)` |
| **set driving speed to ( ) percent** | `movement_speed = 40` (plus `global movement_speed` in `main`) |

### Units

**Centimetres** and **rotations** both become motor degrees and use
`move_for_degrees`, so the distance is exact. **Seconds** uses
`move_for_time` instead.

Direction is handled differently by the two, and the difference is not
cosmetic: `move_for_degrees` drives backward with a **negative distance**,
while `move_for_time` has no distance to negate and so uses a **negative
velocity**.

### Steering

0 drives straight, +100 spins right, −100 spins left, and values in between
mix the wheels proportionally. This is LEGO's convention.

**"Turn right" generates steering +100** — right is clockwise, so the heading
decreases. If your robot turns the wrong way, the drive motors are swapped,
not the block.

### Waiting and not waiting

**drive for** and **turn for** wait until the movement is finished — they
`await`. **start driving** does not: it sets the motors going and moves
straight on to the next block. That is the pairing a line follower needs, and
it matches the official blocks.

## Motors

For a single motor — an arm, a claw, anything that is not a drive wheel.

| Block | Generates |
| --- | --- |
| **run motor (port) for ( ) degrees** | `await motor.run_for_degrees(port.A, 90, velocity_from_percent(MOTOR_SPEED_PERCENT))` |
| **start motor (port) at ( ) percent** | `motor.run(port.A, velocity_from_percent(50))` |
| **stop motor (port)** | `motor.stop(port.A)` |

Single motors use `MOTOR_SPEED_PERCENT`, a constant in the generated program,
rather than the driving speed — an arm and a drive base rarely want the same
speed.

**Using these on ports A or B fights the driving blocks**, on the simulator
and on hardware alike.

## Sensors

These are value blocks: they plug into other blocks rather than standing alone.

| Block | Type | Generates |
| --- | --- | --- |
| **colour sensor (port) sees (colour)** | true/false | `color_sensor.color(port.C) == color.BLACK` |
| **reflected light at (port)** | number | `color_sensor.reflection(port.C)` |
| **distance at (port) in millimetres** | number | `distance_sensor.distance(port.D)` |
| **force sensor (port) is pressed** | true/false | `force_sensor.pressed(port.E)` |
| **position of motor (port)** | number | `motor.relative_position(port.A)` |

### Reading them

**Reflected light** runs from about 6 on black to 94 on white. It is the value
a line follower steers on, because it changes smoothly as the sensor crosses
an edge — unlike colour, which flips.

**Distance** is **−1 when nothing is in range**, not zero and not a large
number. A program that waits for `distance < 200` will fire immediately on
−1 unless you also check it is positive.

**Colour** compares against a named constant rather than a number, so the
generated Python says `color.RED` and reads like the block does.

## Sound and display

| Block | Generates |
| --- | --- |
| **print ( )** | `print('hello')` |
| **show ( ) on the display** | `await light_matrix.write('hello')` |
| **clear the display** | `light_matrix.clear()` |
| **beep at ( ) hertz for ( ) seconds** | `await sound.beep(440, 500)` |

**print is the important one.** It is how a program talks back — the editor
reads printed messages aloud, and the simulator narrates them. For a student
who cannot see the robot, a well-placed `print` is the difference between a
program that works and a program you can tell is working.

`show on the display` wraps a number in `str()` but leaves an obvious string
literal alone, so the Python stays readable.

Beep seconds are converted to milliseconds at generation time, so 0.5 seconds
reads as `500`.

## Control

| Block | Generates |
| --- | --- |
| **wait ( ) seconds** | `await runloop.sleep_ms(1500)` |
| **wait until ( )** | `await runloop.until(lambda: force_sensor.pressed(port.E))` |

`wait until` wraps its condition in a **lambda**, so it is re-evaluated. Pass
the value instead and it would be checked once and never again.

The toolbox also offers Blockly's standard **repeat**, **repeat while/until**
and **if / else**, plus maths, logic, text and variables. They generate
ordinary Python, and SPIKE blocks nest inside them normally:

```python
for count in range(4):
    await motor_pair.move_for_degrees(
        motor_pair.PAIR_1, degrees_for_distance(250), 0,
        velocity=velocity_from_percent(movement_speed))
```

## Ports

Every port dropdown offers **A** to **F**. The defaults match the simulator's
robot:

| Port | Device |
| --- | --- |
| A | left drive motor |
| B | right drive motor |
| C | colour sensor |
| D | distance sensor |
| E | force sensor |

Plugging a real robot together differently is fine — change the dropdowns. But
the **drive** and **turn** blocks always use ports A and B, because
`motor_pair` is set up once at the top of the generated program. To change
that, edit `robotConfig` in `editor/src/generators/python.js`.

## Warnings

The editor checks the workspace as you build and reports, above the blocks:

- **no start block** — nothing will run
- **more than one start block** — they run one after another, not at once
- **blocks not joined to the start block** — they are left out of the program

These are warnings, not errors. The program still generates from whatever is
properly connected.

## Two calibration numbers

`degrees_for_distance` and `degrees_for_turn` depend on the wheel diameter and
the axle track, which live in `editor/src/generators/python.js`:

```js
export const robotConfig = {
  wheelDiameterMm: 56,
  axleTrackMm: 160,
  leftPort: 'A',
  rightPort: 'B',
};
```

**These must match the robot you are driving** — and the simulator's
`--wheel-diameter` and `--axle-track` if you are using it. Get them wrong and
every distance and every turn is wrong in proportion, while the blocks, the
Python and the tests all look perfectly fine.

Measure the axle track between the centres of the two wheels' contact
patches. See [Matching your robot](simulator.md#matching-your-robot) for why
the defaults are what they are, and the mistake that taught us to say this
twice.

## Adding a block

1. Define it in `editor/src/blocks/definitions.js`. **Write the message as a
   spoken sentence** — a screen reader reads the block's text with its fields
   spliced in, so "drive forward for 25 centimetres" has to work aloud. That
   rules out terse labels: a "cm" dropdown reads as two letters, so the option
   says "centimetres".
2. Give every value input a shadow default in `blocks/toolbox.js`. Filling an
   empty socket by keyboard is several extra moves.
3. Write its generator in `editor/src/generators/python.js`.
4. Add a text assertion to `test/generator.test.js` **and** a behaviour
   assertion to `test/e2e.test.js`. Text alone will pass a reversed sign.
